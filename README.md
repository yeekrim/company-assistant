# Company Assistant

[한국어](README.ko.md)

社内規程やマニュアルをもとに社員の質問に答える、会社ごとの AI チャットボットです。管理者が PDF・Word・テキストの文書をアップロードすると、その会社の社員だけがそれらの文書を根拠にした回答を受け取れます。「規程のどこに書いてあるか探す」手間を減らすことを目的に、React／TypeScript のフロントエンドから FastAPI のバックエンド、DB、認証まで一人で開発しました。

---

## 主な機能

- **文書をもとにした質問応答**：社員が自然な文章で質問すると、アップロード済みの文書から関連する部分を探し、その内容だけを根拠に回答します。文書にない内容は推測せず「見つからなかった」と答えます
- **会社ごとのデータ分離と権限**：ログインしたユーザーの会社の文書だけが検索対象になります。文書のアップロード・削除・施行日の変更は管理者だけが行えます
- **規程の新旧版の使い分け**：同じ規程の版を施行日つきで登録しておくと、その時点で有効な版に従って答え、どの版（施行日）を根拠にしたかも示します。「2020年には〜」のような過去の時点の質問にはその時点の版から答えます
- **表の構造化保存**：PDF・Word の表を行・列・型を保ったまま会社ごとの DB に保存します（表を SQL で集計して答える機能は評価中で、まだ回答には使っていません）
- **会話の履歴管理**：会話ごとに履歴が保存され、サイドバーから過去の会話を開いたり削除したりできます

## 技術スタック

| 分類 | 技術 | 用途・選んだ理由 |
|---|---|---|
| Frontend | React 19, TypeScript, Vite | 画面の実装。API のレスポンス形式を型で固定するため TypeScript を使用 |
| 状態管理 | Zustand | 認証情報と、会話ごとの読み込み状態の管理 |
| Backend | FastAPI, SQLAlchemy（async） | API・認証・RAG 処理。埋め込みモデルなど Python の AI ライブラリをそのまま使えるため |
| DB | PostgreSQL 16 | 会社・ユーザー・会話・メッセージ |
| ベクトル DB | ChromaDB | 文書の分割単位（チャンク）の埋め込みと類似検索。会社ごとにコレクションを分けて保存 |
| 表データ | DuckDB | 文書内の表。会社ごとに別ファイルにし、列の型を保ったまま SQL で扱えるようにするため |
| 埋め込み | sentence-transformers（paraphrase-multilingual-MiniLM-L12-v2） | 韓国語の文書を扱うため多言語モデルを使用 |
| LLM | NVIDIA NIM（Nemotron 3 Super 120B A12B） | 回答生成。ローカル LLM（llama3.2 → gemma3:4b）から移行 |
| 認証 | JWT（python-jose）, bcrypt | ログインと API の権限チェック |
| インフラ | Docker Compose | PostgreSQL と ChromaDB をローカルで起動 |

## システム構成

**文書アップロード（管理者）**

1. フロントエンドから文書と施行日を `POST /api/documents` に送信
2. バックエンドで本文を抽出してチャンクに分割し、埋め込みを計算して ChromaDB の `company_{会社ID}` コレクションに保存
3. 同時に文書内の表を抽出し、会社ごとの DuckDB ファイルに保存

**質問応答（社員）**

1. `POST /api/chat` で JWT からユーザーと会社を特定
2. 質問文に「2020年」などの時点があれば、その時点までに施行された文書だけに絞って ChromaDB から上位 10 件を検索
3. 同じ会話の直近メッセージ 6 件のうち、質問と似ているもの（コサイン類似度 0.7 以上）だけを履歴として追加
4. 検索結果と履歴を LLM に渡して回答を生成し、質問と回答を PostgreSQL に保存

## 工夫した点・技術的な課題

### 1. 回答待ちの間に会話を切り替えると表示が混ざる

- **課題**：LLM の回答を待っている間に別の会話へ移ると、ローディング表示が移動先の会話に出たり、届いた回答が別の会話に追加されたりしていました
- **対応**：読み込み状態を全体で 1 つのフラグとして持つのをやめ、「どの会話が読み込み中か」（`loadingConversationId`）で管理するようにしました。回答が届いたとき、リクエストを送った会話と表示中の会話が違えば画面には追加しません。読み込み中の会話に戻ったときは、DB を再取得せずに保持していたメッセージを復元します
- **結果**：回答の生成中に会話を行き来しても、それぞれの会話の内容とローディング表示が正しく保たれるようになりました

### 2. 規程が改正されると古い内容で答えてしまう

- **課題**：同じ規程の新旧版を両方アップロードすると、検索で古い版の条文が混ざり、現在とは違う数値で答えることがありました。逆に「2016年当時は？」という質問に最新版で答えてしまうこともありました
- **対応**：文書ごとに施行日を登録できるようにし、ChromaDB のメタデータに `YYYYMMDD` の整数で保存しました（数値の範囲フィルタ `$lte` を使うため）。質問文から時点を読み取り、その日までに施行された文書だけを検索します。さらにプロンプトで「基準日以前に施行された版のうち最も新しいものに従い、根拠の版を示す」よう指示しています
- **結果**：同じ規程の 3 つの版を使った 12 問の評価で、正答数が 4/12 から 6/12 に上がりました。ただし過去の時点を問う質問は 2/6 にとどまっており、改善の余地があります

### 3. 表データの値が変わってしまう

- **課題**：表を数値に変換して保存する際、社員番号 `018100002` のように 0 で始まるコードが数値になり、先頭の 0 が消えていました。また、重複した列名に番号を付けると、既にある列名とぶつかることがありました
- **対応**：0 で始まる値を含む列は文字列のまま保存し、重複した列名には既存の名前と重ならない番号を付けるようにしました。どちらもテストを追加して確認しています
- **結果**：元の表の値を保ったまま保存できるようになりました

### 4. 小さな不具合をテストで再発させない

- **同じ文書の再アップロード**：チャンク数が減ると古いチャンクが残り、削除済みの内容で答えていました。保存前にその文書のチャンクを削除するようにし、テストを追加しました
- **メッセージの順序**：RAG 処理の後でまとめて保存していたため、質問の作成時刻が回答より遅くなり、表示順が逆になることがありました。質問の時刻を処理の前に記録するようにしました

### 5. 改善を数値で判断する

検索方式や回答方式を変えるたびに感覚で判断しないよう、評価用のハーネスを `experiments/` に用意しました。

- `retrieval_eval`：実際の公共機関の規程などで正解ラベルを作り、nDCG で検索方式を比べます
- `sql_harness`：表の質問を SQL で答える方式を複数試し、正答率・応答時間・トークン数を比べます。今のところ既存の方式を上回る方式がないため、本体には入れていません

## セットアップ・実行方法

### 必要な環境

- Docker Desktop
- Python 3.12
- Node.js 20 以上
- NVIDIA NIM の API キー（build.nvidia.com で発行）

### 起動手順

```bash
# 1. リポジトリをクローン
git clone https://github.com/yeekrim/company-assistant.git
cd company-assistant

# 2. DB を起動（PostgreSQL: 5432, ChromaDB: 8001）
cp .env.example .env              # POSTGRES_PASSWORD を設定
docker compose up -d

# 3. バックエンド
cd backend
cp .env.example .env              # DATABASE_URL, SECRET_KEY, NVIDIA_API_KEY を設定
python -m venv venv
source venv/bin/activate
pip install -r requirements.txt
python seed.py                    # デモ用の会社・ユーザーを作成
uvicorn app.main:app --reload

# 4. フロントエンド（別のターミナルで）
cd frontend
npm install
npm run dev                       # http://localhost:5173
```

`seed.py` は 2 社分のデモユーザーを作ります。ログイン ID は `社員番号@ドメイン`（例：管理者 `admin@virtual.co.kr`、社員 `018100002@virtual.co.kr`）、パスワードはすべて `pass1234` です。

### テスト

```bash
cd backend
pytest
```
