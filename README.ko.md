# Company Assistant

[![CI](https://github.com/yeekrim/company-assistant/actions/workflows/ci.yml/badge.svg)](https://github.com/yeekrim/company-assistant/actions/workflows/ci.yml)

[日本語](README.md)

사내 규정·매뉴얼을 바탕으로 직원의 질문에 답하는 기업용 AI 챗 애플리케이션입니다.

관리자가 PDF·Word·텍스트 형식의 문서를 등록하면, 직원은 자연어로 질문해 관련 규정이나 매뉴얼 내용을 확인할 수 있습니다. 문서를 찾는 데 드는 수고를 줄이고, 필요한 정보에 효율적으로 접근할 수 있도록 하는 것을 목표로 개발했습니다.

프런트엔드부터 백엔드, 데이터베이스, 인증, RAG 처리, 테스트까지 개인으로 설계·구현했습니다.

## 주요 기능

- **문서 기반 AI 챗**: 등록된 문서에서 관련 정보를 검색하고, 그 내용을 근거로 답변합니다. 문서에서 답을 찾지 못하면 추측하지 않고 그렇다고 알려 줍니다.
- **답변 근거 표시**: 답변 아래에 근거로 참조한 문서명·시행일·청크 원문을 보여 줍니다. 지난 대화를 다시 열어도 확인할 수 있습니다.
- **기업별 데이터 분리와 접근 제어**: 로그인한 사용자의 소속 기업에 따라 검색 대상을 제한합니다. 문서 등록·삭제·시행일 변경은 관리자만 할 수 있습니다.
- **규정 개정 이력 대응**: 문서의 시행일을 관리하고, 질문이 묻는 시점에 맞는 판을 검색합니다. 답변의 근거가 된 판도 함께 보여 줍니다.
- **표 데이터 구조화 저장**: PDF·Word 속 표를 추출해 행·열·데이터 타입을 유지한 채 저장합니다.
- **대화 이력 관리**: 대화별로 메시지를 저장하고, 지난 대화를 다시 열거나 삭제할 수 있습니다.

## 기술 스택

| 분류 | 기술 | 용도 |
|---|---|---|
| Frontend | React 19, TypeScript, Vite | UI 구현, 타입 안전한 API 연동 |
| State Management | Zustand | 인증 정보, 대화·로딩 상태 관리 |
| Backend | FastAPI, SQLAlchemy | API, 인증, RAG 처리 |
| RDB | PostgreSQL 16 | 기업·사용자·대화·메시지 관리 |
| Vector Database | ChromaDB | 문서 청크 임베딩 저장과 유사도 검색 |
| Table Data | DuckDB | 추출한 표 데이터 구조화 저장 |
| Embedding | sentence-transformers | 다국어 텍스트 벡터화 |

| Authentication | JWT, bcrypt | 인증, 비밀번호 해싱, API 접근 제어 |
| Infrastructure | Docker Compose | PostgreSQL·ChromaDB 로컬 실행 |
| Testing | pytest | 기능·회귀 테스트 |

## 시스템 구성

### 1. 문서 등록

1. 관리자가 문서와 시행일을 지정해 업로드합니다.
2. FastAPI에서 문서 본문을 추출하고, 검색용 청크로 나눕니다. 규정처럼 조문으로 된 문서는 조·항 단위로 나누고, 부칙(개정 이력)은 검색 대상에서 뺍니다.
3. 청크를 벡터화해 기업 단위 ChromaDB 컬렉션에 저장합니다.
4. 문서 속 표를 추출해 기업별 DuckDB 파일에 저장합니다.

### 2. 질문 답변

1. JWT로 사용자와 소속 기업을 식별합니다.
2. 질문에 대상 시점이 포함되어 있으면, 그 시점까지 시행된 문서로 검색 대상을 좁힙니다.
3. ChromaDB에서 관련성이 높은 청크를 검색합니다.
4. 같은 대화의 최근 메시지 6개 중 질문과의 코사인 유사도가 0.7 이상인 것을 대화 컨텍스트로 고릅니다.
5. 검색 결과와 대화 컨텍스트를 LLM에 넘겨 답변을 생성합니다.
6. 질문·답변과 근거로 넘긴 청크를 PostgreSQL에 저장합니다.

## 기술적 고민과 문제 해결

### 1. 대화 전환 시 상태 관리

**문제**

답변 생성 중에 다른 대화로 전환하면, 로딩 표시나 답변이 엉뚱한 대화에 반영되는 문제가 있었습니다.

**해결**

- 로딩 상태를 대화 ID 단위로 관리하도록 변경
- 요청을 보낸 대화와 현재 보고 있는 대화를 대조해 표시 위치를 제어
- 대화별 메시지를 보관해 두고, 전환 시 복원

**결과**

답변 생성 중에 대화를 전환해도 각 대화의 표시 상태와 메시지가 올바르게 유지되도록 했습니다.

### 2. 규정 개정 이력을 고려한 검색

**문제**

같은 규정의 신구판을 등록하면 검색 결과에 구판 내용이 섞여, 현행 규정과 다른 내용으로 답하는 경우가 있었습니다. 또 과거 시점에 대해 질문했을 때도 당시 규정을 제대로 참조하지 못하는 문제가 있었습니다.

**해결**

- 문서별로 시행일을 관리
- 시행일을 `YYYYMMDD` 형식의 정수로 메타데이터에 저장
- 질문이 묻는 시점에 따라 검색 대상을 좁힘
- 기준일 시점에 유효한 판을 참조하고, 근거가 된 판을 밝히도록 프롬프트를 설계

**결과**

3개 판으로 이루어진 규정으로 만든 12문항 평가(이전 모델 Nemotron 3 Super로 측정)에서 정답 수가 **4/12에서 6/12로 향상**되었습니다. 다만 과거 시점 질문의 정답 수는 2/6에 그쳐, 다음의 "조문 단위 청킹"으로 개선했습니다.

### 3. 조문 단위 청킹으로 검색 정확도 개선

**문제**

답변 근거를 확인해 보니, 출산휴가 질문에서 해당 조문이 LLM에 전달되지 않아 모델이 사전 지식으로 답하고 있었습니다(미숙아 100일이 빠지고, 출산 후 45일 이상 규정도 반대로 설명). 원인은 세 가지였습니다.

- 문서를 500자마다 기계적으로 잘라 조문이나 단어 중간에서 끊겼음
- 임베딩 모델은 앞 128토큰(한국어 조문으로 약 240자)만 읽어서, 500자 청크의 뒷부분이 검색에 반영되지 않았음
- 문서의 절반 가까이를 차지하는 부칙(개정 이력)이 단어만 겹쳐서 본문 조문보다 위로 검색됐음

**해결**

- 조문(제N조)으로 된 문서는 조·항 경계에서 250자 이내로 분할
- 조문이 여러 청크로 나뉘면 뒤 청크에도 조문 제목을 붙임
- 부칙은 검색 대상에서 빼고, 부칙 뒤의 별표(요율표 등)와 개정 이력을 맨 앞에 두는 사규의 본문은 남김
- 조문 형식이 아닌 일반 문서는 기존처럼 500자로 분할

**결과**

같은 12문항 평가(현재 모델 Nemotron 3.5 Super VL, 3회 실행)에서 다음과 같이 개선됐습니다.

| 지표 | 변경 전 | 변경 후 |
|---|---|---|
| 정답 조문이 상위 10개에 포함된 질문 | 6/12 | 12/12 |
| 정답 수 (3회) | 5, 6, 5 | 10, 9, 10 |
| 과거 시점 질문 | 2/6 | 5/6 |

### 4. 표 데이터의 타입과 열 이름 정합성

**문제**

표 데이터를 저장할 때 앞자리가 0인 사번 등이 숫자로 처리되어 원래 값이 바뀌는 문제가 있었습니다. 또 중복된 열 이름에 번호를 붙일 때 기존 열 이름과 충돌하는 경우가 있었습니다.

**해결**

- 앞자리 0을 유지해야 하는 열은 문자열로 저장
- 기존 열 이름과 겹치지 않는 이름을 만드는 처리를 구현
- 각 경우에 대한 테스트 추가

**결과**

원본 데이터 값을 유지하면서 표 데이터를 구조화해 저장할 수 있게 했습니다.

### 5. 테스트를 통한 회귀 방지

개발 중 발견한 버그를 고치는 데서 끝내지 않고, 같은 문제가 다시 생기지 않도록 테스트를 추가했습니다.

- **문서 재업로드**: 청크 수가 줄었을 때 옛 청크가 남는 문제를 고쳐, 갱신 전에 기존 청크를 삭제하는 처리를 추가
- **메시지 시간순 관리**: 답변 생성 후에 질문을 저장해 표시 순서가 뒤바뀌는 문제를 고쳐, 질문 생성 시각을 처리 시작 시점에 기록

### 6. 평가 하네스를 통한 개선 검증

검색·답변 방식의 변경을 감으로만 판단하지 않도록, 평가용 스크립트로 비교할 수 있게 했습니다.

- **`retrieval_eval`**: 정답 라벨을 붙인 규정 데이터로 nDCG를 이용해 검색 방식을 비교
- **`answer_eval` / `chunk_recall`**: 판이 다른 규정 12문항으로 답변 정답 수와 정답 청크 검색 여부를 비교
- **`sql_harness`**: 표에 관한 질문에 대한 SQL 생성 방식을 정답률·응답 시간·토큰 수로 비교

표 데이터에 대한 SQL 기반 답변 생성은 아직 기존 방식보다 나은 결과를 얻지 못해, 일반 답변 처리에는 넣지 않았습니다.

## 설치·실행 방법

### 필요한 환경

- Docker Desktop
- Python 3.12
- Node.js 20 이상
- NVIDIA NIM API 키

### 1. 저장소 가져오기

```bash
git clone https://github.com/yeekrim/company-assistant.git
cd company-assistant
```

### 2. 데이터베이스 실행

```bash
cp .env.example .env
```

`.env`에 `POSTGRES_PASSWORD` 등 필요한 설정을 합니다.

```bash
docker compose up -d
```

PostgreSQL은 5432번 포트, ChromaDB는 8001번 포트로 실행됩니다.

### 3. 백엔드 실행

```bash
cd backend
cp .env.example .env
```

`.env`에 `DATABASE_URL`, `SECRET_KEY`, `NVIDIA_API_KEY` 등 필요한 환경 변수를 설정합니다.

```bash
python -m venv venv
source venv/bin/activate
pip install -r requirements.txt
python seed.py
uvicorn app.main:app --reload
```

`seed.py`는 로컬 확인용 기업·사용자 데이터를 만듭니다.

### 4. 프런트엔드 실행

다른 터미널에서 실행합니다.

```bash
cd frontend
npm install
npm run dev
```

브라우저에서 `http://localhost:5173`에 접속합니다.

### 5. 테스트 실행

backend 디렉터리에서 실행합니다. 테스트는 실제 DB·LLM에 접속하지 않아서 `.env` 없이도 실행됩니다. PR마다 GitHub Actions에서도 백엔드 테스트와 프런트엔드 lint·build를 실행합니다.

```bash
pytest
```

## 향후 개선점

- 질문과 규정의 표현이 다를 때("비슷한 경력"과 "유사경력" 등)의 답변 정확도 향상
- PDF 표를 행·열 구조를 유지한 채 답변에 활용
- 새 청크에 대한 검색 평가(nDCG) 라벨 재작성
- "작년" 같은 상대적 시점 표현 지원
- 표 데이터에 대한 SQL 답변 방식 평가와 도입 판단
- 여러 워커로 실행할 때 DuckDB 파일 동시 쓰기 대책
