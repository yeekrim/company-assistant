# Company Assistant

[![CI](https://github.com/yeekrim/company-assistant/actions/workflows/ci.yml/badge.svg)](https://github.com/yeekrim/company-assistant/actions/workflows/ci.yml)

[한국어](README.ko.md)

社内規程・マニュアルをもとに、従業員の質問に回答する企業向けAIチャットアプリケーションです。

管理者がPDF・Word・テキスト形式の文書を登録すると、従業員は自然言語で質問し、関連する規程やマニュアルの内容を確認できます。文書の検索にかかる手間を減らし、必要な情報へ効率的にアクセスできることを目指して開発しました。

フロントエンドからバックエンド、データベース、認証、RAG処理、テストまで、個人で設計・実装しています。

## 主な機能

- **文書に基づくAIチャット**：登録文書から関連情報を検索し、その内容を根拠として回答。文書内に回答を見つけられない場合は、推測せずにその旨を返します。
- **回答根拠の表示**：回答の下に、根拠として参照した文書名・施行日・チャンク原文を表示します。過去の会話を開いても確認できます。
- **企業ごとのデータ分離とアクセス制御**：ログインユーザーの所属企業に応じて検索対象を制限。文書の登録・削除・施行日の変更は管理者のみ実行できます。
- **規程の改定履歴への対応**：文書の施行日を管理し、質問の対象時点に応じて適切な版を検索。回答の根拠となった版も提示します。
- **表データの構造化保存**：PDF・Word内の表を抽出し、行・列・データ型を保持して保存します。
- **会話履歴の管理**：会話ごとにメッセージを保存し、過去の会話の再表示・削除に対応します。

## システム構成

### 1. 文書登録

1. 管理者が文書と施行日を指定してアップロードします。
2. FastAPIで文書本文を抽出し、検索用のチャンクに分割します。規程のように条文で構成された文書は条・項の単位で分割し、附則（改正履歴）は検索対象から除外します。
3. チャンクをベクトル化し、企業単位のChromaDBコレクションに保存します。
4. 文書内の表を抽出し、企業ごとのDuckDBファイルに保存します。

### 2. 質問への回答

1. JWTからユーザーと所属企業を特定します。
2. 質問に対象時点が含まれる場合、その時点までに施行された文書に検索対象を絞ります。
3. ChromaDBから関連性の高いチャンクを検索します。
4. 同一会話の直近6メッセージから、質問とのコサイン類似度が0.7以上のものを会話コンテキストとして選択します。
5. 検索結果と会話コンテキストをLLMに渡し、回答を生成します。
6. 質問・回答と、根拠として渡したチャンクをPostgreSQLに保存します。

## 技術的な工夫・課題解決

### 1. 会話切り替え時の状態管理

**課題**

回答生成中に別の会話へ切り替えると、ローディング表示や回答が異なる会話に反映される問題が発生しました。

**対応**

- ローディング状態を会話ID単位で管理するよう変更
- リクエスト元の会話と現在表示中の会話を照合し、表示先を制御
- 会話ごとのメッセージを保持し、切り替え時に復元

**結果**

回答生成中に会話を切り替えても、各会話の表示状態とメッセージを適切に維持できるようにしました。

### 2. 規程の改定履歴を考慮した検索

**課題**

同一規程の新旧版を登録すると、検索結果に旧版の記述が混在し、現行規程と異なる内容を回答する場合がありました。一方、過去の時点について質問した際にも、当時の規程を正しく参照できない課題がありました。

**対応**

- 文書ごとに施行日を管理
- 施行日を `YYYYMMDD` 形式の整数としてメタデータに保存
- 質問の対象時点に応じて検索対象を絞り込み
- 基準日時点で有効な版を参照し、根拠となった版を示すようプロンプトを設計

**結果**

3つの版からなる規程を用いた12問の評価（旧モデル Nemotron 3 Super で測定）で、正答数が **4/12から6/12に向上**しました。ただし、過去時点に関する質問の正答数は2/6にとどまり、次の「条文単位のチャンク分割」で改善しました。

### 3. 条文単位のチャンク分割による検索精度の改善

**課題**

回答の根拠を確認したところ、出産休暇の質問で該当条文がLLMに渡されておらず、モデルが事前知識で回答していました（未熟児の場合の100日が抜け、産後45日以上という規定も逆に説明）。原因は次の3点でした。

- 文書を500文字ごとに機械的に分割していたため、条文や単語の途中で切れていた
- 埋め込みモデルは先頭128トークン（韓国語の条文で約240文字）しか読まないため、500文字チャンクの後半が検索に反映されていなかった
- 文書の半分近くを占める附則（改正履歴）が、単語が重なるだけで本文の条文より上位に検索されていた

**対応**

- 条文（第N条）で構成された文書は、条・項の境界で250文字以内に分割
- 条文が複数のチャンクに分かれる場合、後ろのチャンクにも条文タイトルを付与
- 附則は検索対象から除外し、附則の後ろにある別表（料率表など）や、改正履歴を冒頭に置く社内規程の本文は残す
- 条文形式でない一般文書は従来どおり500文字で分割

**結果**

同じ12問の評価（現行モデル Nemotron 3.5 Super VL、3回実行）で次のように改善しました。

| 指標 | 変更前 | 変更後 |
|---|---|---|
| 正解の条文が上位10件に含まれる質問 | 6/12 | 12/12 |
| 正答数（3回） | 5, 6, 5 | 10, 9, 10 |
| 過去時点に関する質問 | 2/6 | 5/6 |

### 4. 表データの型と列名の整合性

**課題**

表データを保存する際、先頭にゼロを含む社員番号などが数値として扱われ、元の値が変わる問題がありました。また、重複する列名に連番を付与する際、既存の列名と衝突する場合がありました。

**対応**

- 先頭のゼロを保持する必要がある列は文字列として保存
- 既存の列名と重複しない名前を生成する処理を実装
- それぞれのケースに対するテストを追加

**結果**

元データの値を保持しながら、表データを構造化して保存できるようにしました。

### 5. テストによる回帰防止

開発中に発見した不具合を修正するだけでなく、同様の問題が再発しないようテストを追加しました。

- **文書の再アップロード**：チャンク数が減少した場合に古いチャンクが残る問題を修正し、更新前に既存チャンクを削除する処理を追加
- **メッセージの時系列管理**：回答生成後に質問を保存することで表示順が逆転する問題を修正し、質問の作成時刻を処理開始時に記録

### 6. 評価用ハーネスによる改善検証

検索・回答方式の変更を感覚だけで判断せず、評価用スクリプトで比較できるようにしました。

- **`retrieval_eval`**：正解ラベルを付与した規程データを用いて、nDCGにより検索方式を比較
- **`answer_eval` / `chunk_recall`**：版の異なる規程12問で、回答の正答数と正解チャンクの検索有無を比較
- **`sql_harness`**：表に関する質問へのSQL生成方式を、正答率・応答時間・トークン数で比較

表データへのSQLによる回答生成は、現時点では既存方式を上回る結果が得られていないため、通常の回答処理には組み込んでいません。

## セットアップ・実行方法

### 必要な環境

- Docker Desktop
- Python 3.12
- Node.js 20以上
- NVIDIA NIM APIキー

### 1. リポジトリの取得

```bash
git clone https://github.com/yeekrim/company-assistant.git
cd company-assistant
```

### 2. データベースの起動

```bash
cp .env.example .env
```

`.env` に `POSTGRES_PASSWORD` など必要な設定を行います。

```bash
docker compose up -d
```

PostgreSQLは5432番ポート、ChromaDBは8001番ポートで起動します。

### 3. バックエンドの起動

```bash
cd backend
cp .env.example .env
```

`.env` に `DATABASE_URL`、`SECRET_KEY`、`NVIDIA_API_KEY` など必要な環境変数を設定します。

```bash
python -m venv venv
source venv/bin/activate
pip install -r requirements.txt
python seed.py
uvicorn app.main:app --reload
```

`seed.py` はローカル検証用の企業・ユーザーデータを作成します。

### 4. フロントエンドの起動

別のターミナルで実行します。

```bash
cd frontend
npm install
npm run dev
```

ブラウザで `http://localhost:5173` にアクセスします。

### 5. テストの実行

バックエンドディレクトリで実行します。テストは実際のDB・LLMに接続しないため、`.env` がなくても実行できます。PRごとにGitHub Actionsでもバックエンドのテストとフロントエンドのlint・buildを実行しています。

```bash
pytest
```
